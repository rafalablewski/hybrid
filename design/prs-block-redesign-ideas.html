Today → the Activity card → New PRs

Two records. Four hairlines. It reads like a receipt.

The block itself is right — records belong to the window the athlete picked, so a month view lists the month's PRs. What's wrong is the treatment. A record is the most emotional figure in the app and it is currently set at the same size, weight and rhythm as a settings row, fenced by more rules than it has content. Ten ways to fix that, from pure subtraction to deleting the block outright — then the one I'd ship.

The three faults

One — the rules outnumber the content. A section rule, then a hairline above every row including the first. Four drawn lines to separate two items that whitespace would have separated for free. The card already sits inside a border; everything inside it is a second fence.

Two — a record is typed like a list item. 13 px, the same size as the label beside it. Nothing on screen says this is the best that lift has ever been. Scale is the cheapest celebration there is and the block spends none of it.

Three — the number stands with no proof. "90 kg" is only an achievement against the 82.5 it beat. PrHit already carries previousTopLoad and the block already imports strengthPrDelta — the evidence is in hand and mostly goes unprinted.

Everything below uses the same data the block reads today: lift, topLoad, previousTopLoad, and the first-ever / more-reps shapes strengthPrDelta already formats. No new engine, no new query.

Three modifiers

Each one composes with any base above

It should arrive, not appear

A record is a moment. When the block first renders after a session that set one, count the number up from the previous best to the new one over ~600 ms and let the caption fade in behind it. Once per session, never on a re-render, and skipped entirely under useReducedMotion() — where the final value is simply there.

Every record opens its session

The card already teaches that figures open. Make each record pressable to the session that set it, reusing the caret-and-drawer the metrics use rather than a new sheet. Proof becomes one press away, and the block inherits the interaction the athlete already learned two rows above.

Name the window, and stay silent when it's empty

"New PRs" is period-blind while the card underneath it is period-aware. Say records this week / in July / this year so a month view can't be misread as recent news. The existing silence at zero is right — never render an empty state that says "no records".

  1. 01Every hairline inside the block goes. The one rule that stays is the card's own section divider, which already separates the figures from what follows — that rule is load-bearing, the other three were decoration.
  2. 02The record is set as a figure: mono, fs.display, 800, tabular, in the lime text token — the same treatment the tonnage and hours columns get, so the block reads as part of the card rather than an appendix.
  3. 03Under each figure, the proof in ash: from 82.5 with the delta in lime, first time, or more reps. All three shapes already come out of strengthPrDelta, so the wording can't drift from the session summary.
  4. 04At one or two records the cells sit still — no rail, no fade, nothing to drag. A single record takes the full width rather than leaving half the row empty; two split it. At three the same cells become a horizontal rail. One component, one cell, a switch on prs.length; a rail that can't move is worse than no rail.
  5. 05A cell is half the content column — the width the two-up grid gives it — so going from two records to three resizes nothing: the third simply appears past the right edge. The peek is the affordance — nothing needs an arrow, a dot row or a "swipe" label to say it moves.
  6. 06The edges dissolve, and only where something is hidden: 24 px of fade on the right while records remain, on the left once you've scrolled past the first, and none at all on an edge that has nothing behind it. A permanent fade on both sides is decoration; a conditional one is a status.
  7. 07Snap is proximity, not mandatory — a flick lands cleanly, a small drag is left where it was put. Same feel as the exercise-widget rail the athlete already knows.
  8. 08The kicker names the window ("Records this week", "Records in July") and each cell presses through to its session. Silence at zero is kept exactly as it is.

The rail is full-bleed. Reading the component settled a question the mock couldn't: this block is a sibling of the Activity card, not a child of it — it sits directly on the screen, under the card, with only the screen gutter beside it. So the house rule applies in its normal form: negative margins the width of the gutter with matching internal padding, and cards slide under the physical screen edge. Resting cells still line up with the content column, and the dissolve now happens at the true edge rather than mid-content, which is where a fade belongs.

Per client. Web: overflowX: "auto", scrollSnapType: "x proximity" and the fade as a maskImage driven by two @property lengths, so it eases rather than snaps (.pr-rail in globals.css). Mobile: a horizontal ScrollView at decelerationRate="fast" — the mobile twin of proximity snap, and the feel every other rail in the app has — with the fade as two LinearGradient overlays in the SCREEN colour, their opacity animated on the native driver; the idiom coach-rail.tsx already ships. Both clients cap the rail at eight records with a final See all 23 cell into the drawer, so a year view can't become an endless drag.

Reach. The rail is focusable and arrow-key scrollable on web with a visible focus ring, and carries a group label naming the window and the count, so the records are readable without a drag. Under prefers-reduced-motion / useReducedMotion() the fades switch instantly instead of easing, and the count-up modifier stays off.

Nothing here needs a new engine call, a new query or a new colour. It is the same prsBetween() output the block already reads, spending its budget on scale and evidence instead of on ink.
